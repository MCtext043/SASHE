# Годовой обзор качества лекарственных препаратов — MVP

Локальное веб-приложение для подготовки **черновика** годового обзора качества продукции (PQR/APQR). Оно собирает CSV/XLSX и данные через адаптер источника, показывает происхождение записей, применяет профиль препарата и площадки, помогает проверить тенденции и передать версию на внутреннюю проверку. Проект подготовлен как демонстрационный прототип для «Биннофарм Групп». Все встроенные примеры вымышлены.

## Быстрый запуск

Нужны Docker Desktop с запущенным движком и Docker Compose.

```powershell
docker compose up --build
```

После запуска:

- интерфейс: http://localhost:3000
- API и документация OpenAPI: http://localhost:8000/docs
- проверка API: http://localhost:8000/health

Войдите под одной из локальных демонстрационных учётных записей:

| Роль | Логин | Пароль |
| --- | --- | --- |
| Автор | `author` | `DemoAuthor2026!` |
| Проверяющий | `reviewer` | `DemoReviewer2026!` |
| Администратор | `admin` | `DemoAdmin2026!` |

Для работы с обзором используйте роль автора. Кнопка **«Открыть демо»** создаёт обзоры вымышленного препарата за 2024 и 2025 годы. Локальный имитатор источника доступен во вкладке «Исходные данные»: для некоторых сочетаний параметров он возвращает вымышленные записи, для остальных — явную заглушку «Источник не содержит записей». Пустой ответ не равен подтверждённому нулю событий. Можно также скачать шаблон CSV, заполнить его и загрузить. Дата — `ГГГГ-ММ-ДД`, кодировка CSV — UTF-8 или Windows-1251; разделители `,` и `;`. Первая строка XLSX содержит названия столбцов.

Остановка: `docker compose down`. Данные сохраняются в именованном томе `postgres_data`. Для полного удаления демонстрационной базы: `docker compose down -v` — команда удаляет данные проекта.

## Возможности

1. Создание обзора по препарату, площадке и отчётному году.
2. Импорт CSV/XLSX по 16 разделам: исходное сырьё, упаковочные материалы, серии, контроль процесса, контроль качества, отклонения, OOS/OOT, изменения, рекламации, CAPA, стабильность, отзывы, изменения в регистрационном досье, валидация, оборудование и помещения, технические соглашения.
3. Предварительная проверка обязательных столбцов, пустых значений, формата и года даты, числовых показателей, границ спецификации и повторных идентификаторов. Файл с ошибками не записывается.
4. Реестр источников импорта с именем файла, количеством строк, датой и SHA-256. Повторная загрузка того же файла отклоняется.
5. Сводные показатели, список разделов без данных, графики результатов с границами спецификации и счётчик значений вне границ.
6. Редактируемые заключение специалиста и предлагаемые действия. PDF содержит сводку, тренды, реестр загруженных сведений, пропуски, заключение и источники.
7. Объяснимые ранние сигналы: четыре последовательных изменения показателя, приближение к границе (15% диапазона) и выход за указанные границы. Сигнал содержит правило и номера записей.
8. Хронология серии объединяет записи разных разделов только по точному номеру серии.
9. Выводы с доказательствами сохраняют текст специалиста и конкретные записи; источники показаны на экране и в PDF.
10. Сравнение с предыдущим годом для того же препарата и площадки: количества, частоты событий на 100 серий и средние значения совпадающих показателей.
11. Подтверждение отсутствия событий с указанием источника и проверившего. Подтверждённый ноль отличается от отсутствующих данных и может быть отозван.
12. Версионный профиль данных по препарату и площадке: обязательные разделы, дополнительные колонки и порог раннего сигнала. Администратор создаёт новую версию, исторический обзор сохраняет назначенную версию.
13. Односторонний импорт через HTTP JSON или подключаемый модуль `app.connectors.*`: сверка числа строк, стандартная проверка записей, происхождение и защита от повторной выгрузки. Встроенный источник — только имитатор.
14. Локальный вход, роли автора, проверяющего и администратора. Подготовлен OIDC Authorization Code + PKCE для корпоративного провайдера с проверкой токена и назначением ролей по группам; реальный провайдер не подключён.
15. Журнал действий с цепочкой SHA-256 и проверкой целостности. Это обнаружение изменений, а не самостоятельный неизменяемый регуляторный архив.
16. Внутренний маршрут «черновик → на проверке → проверен / возвращён». Проверенная версия хранит фиксированный PDF и его SHA-256; новая редакция создаёт следующую версию.

**Важное смысловое различие:** «Не проверено» означает, что источник не загружен; «Подтверждено отсутствие событий» означает, что специалист проверил названный источник. Приложение не выводит ноль событий из пустого файла.

## Пользовательский путь

1. Войдите как автор, откройте демо и выберите обзор за 2025 год. В «Сигналах качества» найдите последовательное снижение растворения: значения ещё в пределах спецификации, но четыре последних результата убывают.
2. Нажмите на номер серии внутри сигнала. Откроется хронология записей этой серии; связанные по номеру испытания и отклонения показаны вместе. Совпадение не объявляется причиной.
3. Ниже сравните 2025 и 2024 годы. Частоты отклонений и рекламаций нормированы на 100 серий; при отсутствии серий отображается «н/д».
4. Перейдите в «Исходные данные». Для событийного раздела без записей укажите проверенный источник и своё имя, затем подтвердите отсутствие событий. При необходимости отзовите подтверждение перед загрузкой файла.
5. На вкладке «Отчёт» добавьте сигнал в «Выводы с доказательствами», уточните текст и сохраните. Проверьте номера записей и исходный файл, затем заполните общее заключение и действия.
6. Скачайте PDF. Убедитесь, что в нём есть подтверждения нуля, сравнение лет, доказательные выводы и пометка «черновик».
7. Создайте отдельный обзор с подходящим профилем. Как администратор задайте обязательные разделы и порог; как автор импортируйте данные из файла или локального источника. Пустой ответ источника оставит раздел непроверенным.
8. Заполните обязательные разделы и заключение, передайте обзор на проверку. Войдите как проверяющий: верните с комментарием либо подтвердите версию. Как автор откройте следующую редакцию. Сверьте сохранённый PDF и историю действий.

Точные тексты, правила расчётов и критерии приёмки описаны в [спецификации расширения](docs/product-spec.md).

## Архитектура

```text
Браузер
   │
   ▼
Next.js (интерфейс, :3000)
   │ JSON / multipart / cookie
   ▼
FastAPI (роли, профили, валидация, расчёты, PDF, :8000)
   │ SQLAlchemy + psycopg
   ▼
PostgreSQL 16 (данные в Docker volume)
   ▲
   │ односторонний импорт через API
Локальный имитатор / адаптер LIMS-QMS
```

**Модель данных:** `reviews`, `quality_records`, `import_runs`, `section_attestations`, `evidence_findings` содержат область обзора, записи, происхождение, подтверждения нуля и экспертные выводы. `quality_profiles` и `review_profile_links` закрепляют версию правил; `app_users`, `app_sessions`, `oidc_attempts` обеспечивают доступ; `audit_events`, `audit_head`, `review_workflows`, `review_releases` фиксируют действия и версии. Расчёты остаются в `backend/app/analysis.py`. Подробная схема — в [документе архитектуры](docs/architecture.md).

**Почему такой стек:**

| Решение | Причина |
| --- | --- |
| Локальное веб-приложение | Единый интерфейс для специалистов без установки десктопного клиента; данные остаются в выбранном локальном контуре. |
| Next.js 16 + TypeScript | Удобная компонентная разработка, строгая проверка типов и готовая сборка интерфейса. Серверная часть Next.js здесь не дублирует API. |
| FastAPI + Pydantic | Явные контракты запросов, встроенная OpenAPI документация и удобная обработка файлов на Python. |
| PostgreSQL 16 | Надёжное транзакционное хранение; JSON позволяет начать с разнотипных записей, сохранив общие поля для поиска и агрегации. |
| SQLAlchemy | Отделяет модель хранения от HTTP и позволяет постепенно перейти к более строгим таблицам и миграциям. |
| ReportLab | Формирует PDF на сервере без зависимости от браузерной печати; поддерживает кириллицу с DejaVu Sans в контейнере. |
| Docker Compose | Воспроизводимый локальный запуск четырёх компонентов, включая учебный источник, одной командой. |

**Дизайн:** в боковой панели используется логотип, предоставленный заказчиком для проекта. Интерфейс опирается на спокойную синюю и чёрную палитру корпоративной айдентики и рассчитан на работу с таблицами. Остальные цветовые и типографические токены пока являются адаптацией для MVP; при доступе к внутренней дизайн системе их следует сверить с брендбуком.

## Инженерные границы MVP

- **Реальные LIMS/QMS пока не подключены.** Есть контракт HTTP JSON, точка расширения `backend/app/connectors/`, сверка и атомарный импорт; в Compose работает только имитатор с вымышленными данными. Для площадки нужны спецификация API, реквизиты доступа, сопоставление полей и согласованные тестовые выгрузки. При пустом ответе показана заглушка, импорт и подтверждение нуля не создаются.
- **Корпоративный IdP не подключён.** Подготовлен OIDC Authorization Code + PKCE; требуются issuer, client ID, redirect URI, сопоставление групп с ролями и проверка в контуре заказчика. Локальные демо-учётные записи и пароли из Compose нельзя использовать для реальных данных.
- **Профиль не равен утверждённой SOP.** Версии, обязательные разделы, дополнительные поля и порог доступны администратору, но профиль и метод анализа должны быть согласованы службой качества. Порог 15% — демонстрационное исходное значение. Сигналы помогают проверке и не заменяют статистическую оценку или экспертный вывод.
- **Внутренняя проверка не является юридически значимой электронной подписью или GxP-утверждением.** Проверенная версия хранит PDF и хеш, но PDF остаётся черновиком. Для регулируемого утверждения нужны политика подписи, идентификация подписанта, утверждённый маршрут и регуляторная валидация.
- **Журнал не является независимым неизменяемым архивом.** Цепочка хешей обнаруживает ряд изменений в БД, но администратор БД может изменить данные и пересчитать цепочку. Нужны внешнее хранение/резервные копии, мониторинг, сроки хранения и процедуры восстановления.
- **Нет промышленной GxP-валидации и миграций схемы.** `create_all` создаёт новые таблицы, но не выполняет управляемые изменения существующих. Для использования реальных данных нужны миграции, проверка производительности и отказоустойчивости, контроль доступа, протоколы IQ/OQ/PQ и принятие заказчиком. Демо запускается по HTTP только на `localhost`; в рабочем контуре нужны HTTPS, `COOKIE_SECURE=true`, управление секретами и сетевые ограничения.
- PDF маркирован как черновик. Отсутствие раздела не трактуется как нулевое число событий.

Нормативный ориентир: [Решение Совета ЕЭК № 77 от 03.11.2016, Правила GMP ЕАЭС](https://docs.eaeunion.org/documents/306/2586/). Основа визуального направления: [сообщение «Биннофарм Групп» о корпоративном бренде](https://www.binnopharmgroup.ru/press/news/2021/kholding-binnofarm-grupp-razrabotal-sobstvennyy-korporativnyy-brend/).

## Разработка без Docker для приложения

Для этого варианта PostgreSQL должен уже работать локально с базой `quality`, пользователем `quality` и паролем `quality` (или задайте `DATABASE_URL`).

```powershell
cd backend
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt
$env:DATABASE_URL="postgresql+psycopg://quality:quality@localhost:5432/quality"
$env:AUTH_MODE="local"
$env:LOCAL_ADMIN_PASSWORD="DemoAdmin2026!"
$env:LOCAL_AUTHOR_PASSWORD="DemoAuthor2026!"
$env:LOCAL_REVIEWER_PASSWORD="DemoReviewer2026!"
.venv\Scripts\uvicorn app.main:app --reload
```

В другом терминале:

```powershell
cd frontend
npm ci
$env:NEXT_PUBLIC_API_URL="http://localhost:8000"
npm run dev
```

Таблицы создаются при старте API. Для промышленной эксплуатации следует заменить это на версионируемые миграции.

### Подключение LIMS/QMS и корпоративного входа

Стандартный адаптер читает `GET {SOURCE_BASE_URL}/exports?product=…&site=…&year=…&category=…` с `Authorization: Bearer {SOURCE_API_KEY}`. Ответ: `{"export_id":"unique-id","count":1,"rows":[{"record_date":"2025-01-15",…}]}`. `rows` должны соответствовать базовым колонкам из `/schemas` и дополнительным полям назначенного профиля. Нельзя интерпретировать пустой ответ как отсутствие событий. Если контракт API отличается, скопируйте [пример адаптера](backend/app/connectors/example.py), преобразуйте ответ и задайте `SOURCE_ADAPTER_MODULE=app.connectors.<имя>`; функция `fetch_export(product, site, year, category, settings)` возвращает тот же объект. Адаптер работает только на чтение. URL внешнего источника должен быть HTTPS. Браузерные реквизиты источника не используются.

Для SSO задайте `OIDC_ISSUER` (HTTPS), `OIDC_CLIENT_ID`, `OIDC_REDIRECT_URI` (например, `https://api.example.ru/auth/oidc/callback`), при необходимости `OIDC_CLIENT_SECRET`, `OIDC_GROUPS_CLAIM` и `OIDC_ROLE_GROUPS` — JSON вида `{"author":["pqr-authors"],"reviewer":["pqr-reviewers"],"admin":["pqr-admins"]}`. Приложение сверяет `issuer`, `audience`, `nonce`, подпись ID token по JWKS и использует PKCE. Для отключения локального входа установите `AUTH_MODE=oidc`; `COOKIE_SECURE=true` и HTTPS обязательны в рабочем контуре. Без настроенного IdP кнопка корпоративного входа не отображается. Сопоставление групп и полномочий надо испытать на тестовом IdP заказчика.

Демо-пароли и ключ учебного источника заданы в `docker-compose.yml` только для изолированного локального просмотра. Перед подключением реальных данных замените их переменными окружения/секретами и отключите учебный источник.

### Test coverage

HTTP-тесты проверяют прежние сценарии, а также локальный вход, роли, профиль, пустой и заполненный ответ источника, передачу и возврат проверки, новую версию, фиксированный PDF, обнаружение изменения журнала и учебный OIDC callback с подписанным токеном. Отдельный smoke test проверяет CSV/XLSX, ошибочный и повторный импорт. Тесты используют временную SQLite базу; рабочий запуск использует PostgreSQL. На 27.11.2026 `pytest-cov` показывает **84% строк Python-кода** в `backend/app` (анализ — 94%, основной API — 92%, модуль управления — 81%; пример адаптера и учебный источник не охвачены этим набором тестов). `npm run build` проверяет TypeScript и сборку интерфейса, `npm run lint` — ESLint. OIDC с реальным IdP, адаптеры площадки и GxP-валидация этими тестами не подтверждаются.
